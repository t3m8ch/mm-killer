# Запуск и выпуск приложения

Используем [12 факторов](https://12factor.net/ru/) как договорённости о запуске.
Ниже описан контракт приложения; конкретный production-хостинг пока не выбран.

## Конфигурация

Сервер и мигратор требуют `DATABASE_URL` с протоколом `postgres:` или `postgresql:` и явно заданным хостом.
При отсутствии или некорректном URL процесс завершается с ошибкой, без подстановки
локальной БД и без вывода значения переменной. Конфигурация читается при запуске через `readConfig()` (`@t3-oss/env-core` и схема
Zod). Валидация не выводит значения переменных; чтение серверных переменных
в браузере блокируется. `HOST`/`PORT` и параметры остановки читает Nitro/srvx.
Секреты передаёт среда развёртывания; они не входят в Git или клиентский bundle.
`VITE_*` предназначены для публичных значений: секреты через них передавать нельзя.

Локальные значения для разработки заданы в `mise.toml`, образец — `.env.example`.
Production-процессы запускаются напрямую через Node с окружением от платформы.
`TEST_DATABASE_URL` используется только тестами и указывает на отдельную БД
с правом создавать временные базы.

HTTP слушает `HOST` и `PORT`; у production-рантайма Nitro также есть переменные
`NITRO_HOST` и `NITRO_PORT`, которые имеют приоритет. Для доступности извне задать
`HOST=0.0.0.0` и выделенный платформой `PORT`. TLS завершает внешний reverse proxy.

## Сборка, выпуск и запуск

Стадии выполняются отдельно:

1. **Сборка:** установить зависимости с `pnpm install --frozen-lockfile`, выполнить
   `pnpm build`. Для сборки не требуется `DATABASE_URL` или работающая БД.
   Nitro создаёт `.output/` с HTTP-сервером и клиентскими ресурсами.
2. **Выпуск:** связать собранную ревизию с конфигурацией окружения и присвоить
   выпуску неизменяемый идентификатор, например Git SHA. Выпуск содержит `.output/`,
   `migrations/`, `scripts/migrate.ts`, `src/platform/`, `package.json`,
   `pnpm-lock.yaml` и production-зависимости (`pnpm install --prod --frozen-lockfile`).
   Исходники платформы нужны отдельному CLI миграций; HTTP-серверу достаточно `.output/`.
3. **Администрирование:** из корня того же выпуска выполнить `node scripts/migrate.ts`
   с его `DATABASE_URL`. Платформа запускает эту команду один раз перед обновлением
   HTTP-процессов и прекращает выпуск при ошибке. Параллельные миграции исключает
   механизм блокировки выпуска на платформе.
4. **Запуск:** выполнить `NODE_ENV=production node .output/server/index.mjs`
   или `pnpm start`. Запуск не пересобирает приложение и не меняет схему БД.

Одна сборка продвигается между окружениями с разной runtime-конфигурацией.
Каждый выпуск сохраняет собственные миграции; редактирование файлов работающего
выпуска запрещено. Откат кода не откатывает БД: миграции должны учитывать
совместимость одновременно работающих старых и новых экземпляров.

Команды выше выполняются из корня выпуска. Статические ресурсы входят в сборку;
данные пользователей, загрузки и журналы не сохраняются как единственная копия
в локальной файловой системе HTTP-экземпляра.

## Процессы и завершение

Один HTTP-процесс обслуживает один порт. Число экземпляров задаёт платформа;
каждый экземпляр имеет свой пул соединений с общей БД. Учитывать суммарный размер
пулов при настройке лимита соединений Postgres. Память процесса используется для
временных объектов и соединений; сессии, задания и иное долговечное состояние
должны храниться во внешних сервисах. Локальные файлы и память не обеспечивают
координацию между HTTP-экземплярами.

Git выделяется в отдельный сервис с постоянным хранилищем репозиториев и резервным
копированием. Его файловое хранилище не зависит от жизненного цикла HTTP-экземпляров.
Временные клоны в приложении допустимы, если они восстановимы. Конкретное устройство
Git-сервера и сохранность коммитов попыток обсуждаются в
[задаче #9](https://github.com/t3m8ch/mm-killer/issues/9); эта документация не выбирает
механизм закрепления коммитов или правила force-push.

Nitro получает `SIGTERM`/`SIGINT`, прекращает принимать соединения, завершает HTTP
и вызывает hook закрытия пула Postgres. В закреплённой версии используется srvx:
`SERVER_SHUTDOWN_TIMEOUT` задаёт ожидание HTTP-запросов в секундах, по умолчанию 5.
Обработка сигналов явно включена в server entry, включая окружение CI. Платформа должна предоставлять
время на штатное завершение, затем принудительно останавливать зависший процесс.
Проверка соединения Postgres ограничена 5 секундами.

`GET /health/live` проверяет, что HTTP-процесс отвечает. `GET /health/ready`
выполняет `SELECT 1` и возвращает 200 при доступной БД либо 503 при ошибке.
Эта проверка не подтверждает соответствие схемы ожидаемой версии: это обязанность
отдельного этапа миграции. Платформа использует готовность для подачи трафика;
временная недоступность БД сама по себе не должна запускать цикл рестартов процесса.

Логи приложения пишет Pino в stdout: JSON-строка на событие, уровни задаются через
`LOG_LEVEL` (по умолчанию `info`). Ошибки передавать полем `err`, контекст —
именованными полями; для постоянного контекста операции использовать дочерний
логгер. Поля `DATABASE_URL`, `connectionString`, `password`, `token` и заголовки
авторизации/cookie по настроенным путям скрываются. Это не очистка произвольного
текста: секреты нельзя включать в сообщения и стек ошибок. Логи самого Nitro/srvx
могут оставаться текстовыми в stdout/stderr. Сбор, хранение и поиск выполняет платформа.
Приложение работает в foreground; перезапуск и масштабирование выполняет supervisor.

## Применение факторов

| Фактор                    | Договорённость                                                  |
| ------------------------- | --------------------------------------------------------------- |
| I. Кодовая база           | Один Git-репозиторий, окружения запускают выбранные ревизии     |
| II. Зависимости           | Версии и lockfile закреплены, установка frozen-lockfile         |
| III. Конфигурация         | Значения и секреты приходят из окружения при запуске            |
| IV. Внешние сервисы       | Postgres подключается по URL; смена БД не требует правки кода   |
| V. Сборка, выпуск, запуск | Отдельные стадии, одна сборка для разных окружений              |
| VI. Процессы              | Долговечное состояние находится вне HTTP-процесса               |
| VII. Привязка к порту     | Собственный HTTP-сервер с HOST/PORT                             |
| VIII. Параллелизм         | Масштабирование независимыми экземплярами процесса              |
| IX. Уничтожимость         | Быстрый старт, обработка сигналов, закрытие пула                |
| X. Паритет окружений      | Postgres в разработке, тестах и production; сопоставимые версии |
| XI. Логи                  | Потоки stdout/stderr, хранение снаружи                          |
| XII. Администрирование    | Миграции отдельным процессом из того же выпуска                 |

Свойства хостинга — продвижение артефактов, блокировка выпусков, перезапуски,
масштабирование и сбор логов — нужно настроить при выборе production-платформы.
Репозиторий пока проверяет контракт приложения, а не существующий production-деплой.

## Проверка контракта

После `pnpm build` команда `pnpm test:runtime` запускает временную копию `.output/`
на автоматически выбранном порту, проверяет SSR и статические ресурсы, готовность
при доступной и недоступной БД, сигналы завершения и обязательность конфигурации.
Отдельный процесс миграции проверяется на временной БД. В CI сборка выполняется
без `DATABASE_URL`, затем те же проверки выполняются с тестовым окружением.

Используемые адаптеры: [TanStack Start — hosting](https://tanstack.com/start/latest/docs/framework/react/guide/hosting),
[Nitro — plugins](https://nitro.build/docs/plugins), [srvx](https://srvx.h3.dev/guide).

## Моковый вход и сессии

После миграций выполнить `pnpm db:seed`: команда идемпотентно создаёт двух
пользователей разработки. `/login` позволяет выбрать одного из них; это временный
вход до интеграции Keycloak. Не использовать этот этап как публичную production-систему.

Сессия действует 30 суток без продления. Токен — 32 случайных байта в base64url;
в Postgres хранится SHA-256, исходный токен не сохраняется. Cookie имеет HttpOnly,
SameSite=Lax, Path=/ и Max-Age; Secure включён при HTTPS и всегда в production
за reverse proxy. Вход заменяет текущую сессию. Выход удаляет текущую сессию,
выход со всех устройств — все сессии пользователя. Истёкшие строки не дают доступ.
Даты `created_at` и `updated_at` пользователей и `created_at` сессий обязательны;
seed задаёт одинаковые даты создания и обновления и не меняет существующих пользователей.

`pnpm test:api` проверяет публичный API на отдельной временной БД. Для
`pnpm test:e2e` предварительно выполнить миграции и seed в локальной БД.
