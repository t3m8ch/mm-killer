# Архитектура

Публичные входы каждого модуля определяются glob-паттерном `**/public.*`. Контракт oRPC определяет вход,
выход и типизированные ошибки до реализации обработчиков. Платформа не
зависит от предметных модулей. Сборка приложения связывает модули через
публичные API и передаёт обратные вызовы вместо обратных импортов.

Граф разрешённых зависимостей (стрелка от потребителя к поставщику):

- invitations → courses
- tasks → courses
- attempts → tasks
- reviews → attempts
- git → attempts
- notifications → tasks
- каждый модуль → platform
- app → публичные API модулей, platform

Курсы владеют участием, ролями, подгруппами и состоянием курса; попытки —
допусками и переходами по цепочке. Только владелец таблицы может писать в
неё. Чтение через join допустимо в рамках направленного графа.

Тесты вызывают публичный oRPC API с настоящим Postgres и управляемыми часами.
Обычные тесты откатывают транзакцию, гонки используют независимые соединения.
Вспомогательный тестовый код запрещён в предметном коде.

Общая оболочка MergeMinds (`AppLayout`, Sidebar, крошки и дерево навигации)
находится в `src/platform/navigation` и получает готовые данные через props.
Платформа предоставляет также провайдер темы, базовые UI-примитивы и общий тип `Breadcrumb`.
`AppLayout` получает функцию `renderSidebar` и управляет размещением панели;
данные курсов и пользователя принадлежат отдельному `Sidebar`.
Сборка `src/app/navigation.tsx` связывает маршруты и запросы; корневой маршрут
подключает авторизацию и собирает `Sidebar`. Предметные модули возвращают чистые описания крошек через
свои публичные интерфейсы.

UI модулей использует Mantine и платформенные компоненты. Собственные CSS,
`className`, `style` и UI DSL запрещены. Начальная загрузка выполняется в loader,
данные читаются через useSuspenseQuery. Ошибки и загрузка обрабатываются на
границе маршрута.

Проверка генератора создаёт тестовый модуль только во временном проекте.

## Серверный код и клиентская сборка

Import protection TanStack Start настроена в `vite.config.ts`: файлы `*.server.*`, Node.js built-ins, `pg`, `pg-pool`, `drizzle-orm`,
`@orpc/server` и `nitro` запрещены в клиентском коде. Нарушение вызывает ошибку
при разработке и сборке. SSR-сборка также запрещает `*.browser.*`.
Контракты oRPC доступны клиенту; `import type` удаляется компилятором и допустим.
Серверные ветки TanStack Start удаляются из клиентской сборки до проверки границ.

`pnpm test:bundle` запускает реальные сборки во временном проекте: допустимый
клиент и импорт типа должны собираться, прямой серверный импорт, реэкспорт
и динамический импорт — завершаться ошибкой import protection. Проверка использует
конфигурацию проекта и запускается в CI. Новые серверные библиотеки добавлять
в запреты при их подключении. Защита импортов не проверяет произвольные секреты,
встроенные в строковые литералы или публичные переменные окружения.

## Имена файлов и среды выполнения

Перед расширением ставится суффикс среды: `*.server.ts` — Node/сервер,
`*.shared.ts` — изоморфный код без UI, `*.ui.tsx` (или `.ui.ts`) — UI,
совместимый с SSR, `*.browser.ts` (или `.browser.tsx`) — код только браузера.
UI при загрузке и SSR не обращается к `window`, `document` или browser-only библиотекам.
Суффикс `.browser` не заменяет `.ui`: browser-only код запрещён в SSR-графе.
Тесты сохраняют `.test.ts`; маршруты и связывающий код приложения следуют
именам TanStack/Nitro. Файлы предметных модулей обязаны обозначать среду;
это контролирует Oxlint.

Публичный интерфейс каждой среды задаётся отдельным входом: `public.server.ts`,
`public.shared.ts`, `public.ui.ts`, `public.browser.ts`.
Входы содержат явные реэкспорты; реализации остаются приватными.
Например, `public.ui.ts` реэкспортирует layout из `layout.ui.tsx`; JSX во входе нет.
Все остальные файлы приватны по умолчанию. Easement находит публичные входы
по `src/platform/**/public.*` и `src/modules/<имя>/**/public.*`;
добавлять отдельный файл в конфигурацию не нужно. Общего `index.ts` нет.
Серверный вход экспортирует реализацию, изоморфный — контракт и общие типы,
UI импортируется через собственный вход. Tooling импортирует полные пути с `.ts`,
чтобы встроенное удаление типов Node не требовало TSX или Vite.

`pnpm boundaries` запускает два конфига Easement: `easement.yml` проверяет
предметные границы и приватность, `easement.environments.yml` — среды.
`must_not_reach` запрещает транзитивные цепочки, в том числе через файлы
связывания без суффикса: shared не достигает server/browser/ui, browser не
достигает server, ui не достигает server/browser, server не достигает browser.
Shared, UI и browser также не импортируют integration: файлы без суффикса
не гарантируют среду выполнения, а внешняя серверная библиотека через такой
посредник не должна обходить запреты. Сервер может использовать SSR-совместимый UI.
Изоморфный контракт не экспортируется через серверный вход.

`src/app/client.ts` — HTTP-клиент oRPC для браузера. Серверного прямого
вызова обработчиков и передачи Query-кэша в HTML нет. Страницы и их загрузчики
исполняются в браузере; Nitro заранее создаёт общую оболочку при сборке.
UI с суффиксом `.ui` остаётся пригодным для служебной оболочки; ограничения
серверных импортов и изоморфных контрактов сохраняются.
Прямые зависимости UI и shared от серверных пакетов запрещены конфигурацией
сред; новые библиотеки с ограничением среды нужно добавлять туда и в Vite.

`pnpm test` проверяет новые публичные и приватные входы, транзитивные нарушения
и импорт серверных/изоморфных входов платформы и генератора чистым Node.
`pnpm test:bundle` проверяет публичный UI оболочки, browser-only загрузчики и рендеринг страниц,
а также прямые, динамические импорты и реэкспорты серверного кода в браузере.

## Регистрация типов маршрутов

TanStack Router регистрирует тип приложения через расширение интерфейса `Register`.
Типы метаданных и файловых маршрутов также расширяют внешний модуль
`@tanstack/react-router`. Поэтому типизированные ссылки связаны с объявлениями
в `src/router.tsx`, `src/app/navigation.tsx` и `src/routeTree.gen.ts`.
Такую связь мы сознательно допускаем; обычные зависимости платформы от приложения
и сервера по-прежнему запрещены.

В upstream Easement не было узкой настройки для этого случая. Построчное подавление
убирает сообщение, но оставляет связь в графе для `must_not_reach`. Общее разрешение
`platform -> app` или отключение проверки циклов ослабило бы посторонние границы.
Перенос навигационного UI в `app` устранял конкретный конфликт, но предметным
UI-компонентам также понадобятся ссылки на маршруты, и проблема повторится.
Размещение общей оболочки в платформе позволяет получать готовые данные через props,
оставляя сборку, авторизацию и запросы в приложении.

До согласования и выпуска решения upstream используем
[форк Easement](https://github.com/t3m8ch/easement). Он добавляет явное исключение
`accept_augmentations`: точное имя внешнего модуля и обязательное обоснование `because`.
Необязательные `consumers` и `declaration` позволяют ограничить исключение
компонентами-потребителями и точным файлом объявления. Возможности upstream
обсуждаются в [issue #134](https://github.com/mokevnin/easement/issues/134);
наш API пока является решением форка.

В обоих конфигах мы принимаем неявные связи через расширения
`@tanstack/react-router` во всём проекте: `consumers` и `declaration` не заданы.
Глобальная регистрация типов является штатным механизмом TanStack Router;
перечисление файлов и компонентов лишь заставляло повторять одно решение
при добавлении маршрутов и предметного UI. Новые файлы регистрации и компоненты
подпадают под то же правило автоматически. Точное имя пакета ограничивает исключение:
другие внешние модули и импорты подпутей пакета требуют отдельного решения.
Обычные импорты файлов приложения, явные ссылки на символы расширения
и посторонние транзитивные цепочки продолжают проверяться.

Разрешённые неявные связи не участвуют в проверках зависимостей, достижимости и циклов.
Easement перечисляет применённые исключения с причиной в текстовом отчёте и в
`stats.accepted_augmentations` JSON-отчёта. Индекс сохраняет сведения о типах;
проверки символов не отключаются. Удаление исключения восстанавливает проверки,
в том числе при использовании кешированного индекса.
